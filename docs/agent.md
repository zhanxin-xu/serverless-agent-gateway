# Agent 与对话

每个聊天（一个群、一个私聊）有一条只追加的**事件流**，它是这个聊天唯一的事实来源。设计参照 DeepSeek 的 [dsh](https://github.com/deepseek-ai/deepseek-harness) 的会话日志：收到的消息、模型的每一次输出（包括思维链）、每一次工具调用和结果、每一轮的系统提示，全部按顺序写进去，写了就不改。发给模型的输入是从事件流**推导**出来的。

## 两个解耦的部分

**入口（每个 Webhook 请求）**：验签 → 去重 → 把消息写进事件流 → 判断要不要唤起 agent。入口不碰模型。要唤起时，就在这个 Webhook 函数里接着跑运行者；一轮在这个函数的时长里做不完，才交给内部接口 `/api/worker`，由一个新的函数接着做（见[步数与时间](#步数与时间)）。

| 收到的消息 | 没有 agent 在跑 | 已经有 agent 在跑 |
|---|---|---|
| 私聊 / @ 机器人 | 唤起 | 只写库，正在跑的 agent 下一步就能看到 |
| 群里没 @ | 每个群每 10 秒最多唤起一次 | 只写库 |

**运行者（抢到这个聊天的锁的那个请求）**：一轮接一轮地处理所有还没处理的消息，直到没有待办为止。同一个聊天同一时刻只有一个运行者，所以几个人同时发消息，只会有一个 agent 来回答，不会重复回答。

锁是会话行上的一个会过期的租约（持有者和到期时间，60 秒，运行中每 20 秒续期），函数被杀后最多 60 秒自动释放。运行者的每一次写库（追加事件、推进游标、轮次计数、删除旧事件）都带着锁的持有者，数据库确认它仍然持有锁才会写入：万一续期失败、锁被别的运行者接手，旧的运行者下一次写库就会失败并直接停下，不会和新的运行者交错写事件流，也不会再发消息。入口的**去重、写库、抢锁在同一个事务里**完成；运行者**先释放锁、再检查一次**有没有新消息。两边按这个顺序，消息就不会卡在交接的空隙里被漏掉。

交给 worker 时，运行者先释放锁，worker 再重新抢锁。中间如果被另一条消息的入口抢先，就由那边接着跑：结果一样，都是从事件流继续，抢不到锁的一方直接结束。这样任何时刻都不会有两个函数同时以为自己持有锁。

实现见 [`src/runtime/`](../src/runtime/)：入口 `ingress.ts`、交给 worker `handoff.ts`、采样器 `sampler.ts`、运行者 `runner.ts`、锁 `lock.ts`。

## 一轮对话

一轮从"待处理的消息"开始：游标（处理到哪条了）之后的所有消息。

1. 追加 `turn/start`。普通的一轮不加系统提示：系统提示词里写着规则，上一次 end_turn 之后新来的消息就是这一轮要处理的；群聊里消息头带「@你」的是在叫它，没带的它觉得跟自己有关也可以接话。私聊和群聊各用一段规则（`src/prompt/rules.ts` 的 `SCENE_RULES`），按聊天类型拼在人设和业务规则后面。系统提示由人设、业务规则、场景、渠道格式、每个开启的模块的段落、这个聊天的额外设定拼成，见[模块 · 系统提示怎么拼](modules.md#系统提示怎么拼)。
   发出的消息挂在哪条用户消息上（QQ 被动回复要带它的 `msg_id`）是平台的事，模型不用管：不填 `reply_to` 时，运行时挂到这一轮最新一条 @ 它的消息上，没有就挂到最新一条，都要还能回复。模型只在想显示引用框时，用 `reply_to` 加 `quote: true` 指定引用哪条。只有事件流本身看不出来的情况才加系统提示：这一轮接着上一段继续、之前有消息没能发出去。
2. 每一步：
   - 读取事件流的新事件。这期间来的新消息模型在这一步之后就能读到（见推导规则），挂靠的消息按同样的方式跟着更新，不另加提示。
   - 从事件流推导出输入，调用模型。
   - 把模型的输出**原样**写进事件流（`assistant/message`），包括带 `encrypted_content` 的思维链。
   - 对每个工具调用：先写一条 `tool/call`（准备执行），执行后写 `tool/result`。
3. 模型调用 `end_turn` 挂断，或者到了最后一步，这一轮就结束，追加 `turn/end`，游标推进到这一轮看到过的最新消息。
4. 这个函数的时间不够了，这一轮会以 `paused` 或 `interrupted` 结束，**游标不动**，由新的函数接着这一轮继续，见[步数与时间](#步数与时间)。

实现见 [`src/agent/loop.ts`](../src/agent/loop.ts)。

## 事件格式

每个事件是 `{ seq, type, time, data }`，是 `gateway.events` 表的一行。`seq` 由数据库在追加时按聊天连续编号，删掉前面的事件也不会重新编号。消息头里的"第N条"就是 seq。

| type | 模型可见 | 内容 |
|---|---|---|
| `user/message` | ✅ | 收到的消息：消息头、正文、发送人、是否 @、图片的存储键、平台回复信息 |
| `user/mentioned` | — | 同一条消息又以 @ 事件推送了一次 |
| `session/reset` | — | `/reset`，它之前的内容都不再可见 |
| `turn/start` / `turn/end` | — | 一轮的开始和结束（结束原因：`completed`、`max-steps`、`out-of-time`、`error`、`interrupted`） |
| `step/start` / `step/end` | — | 一步的开始和结束（一次模型调用加它请求的工具） |
| `developer/message` | ✅ | 系统提示：只在接着上一段继续、有消息没发出去、最后一步时才有 |
| `assistant/message` | ✅ | 模型这一步的全部输出，原样保存，附带 `usage` |
| `assistant/attempt` | — | 失败的模型调用 |
| `tool/call` | — | 工具准备执行 |
| `tool/result` | ✅ | 工具结果 |
| `tool/images` | ✅ | `read_file` 打开的图片 |
| `compaction/summary` | ✅ | 压缩摘要，替代 `fromSeq` 之前的全部内容 |
| `bot/sent` | — | 机器人实际发出的一条内容（文字、表情包、语音、文件、运行时的提示），管理端的聊天记录用它 |
| `admin/message` | ✅（当作模型自己说的） | 管理员以机器人身份发的话 |

**推导规则**：从最近一次 `/reset` 之后、最近一条摘要开始，按顺序转换：摘要和用户消息变成 `user` 消息，系统提示变成 `developer` 消息，管理员代发的话变成 `assistant` 消息，模型输出原样展开，工具结果变成 `function_call_output`，其余事件跳过。系统提示词放在 `instructions` 里，不入库，每次请求时由 `src/prompt/assemble.ts` 按这个聊天开启的模块现拼。

两处特殊处理，都只影响推导结果，不改事件流：
- 一步执行期间到达的消息，推导时放在这一步的工具结果之后，保证每个工具调用后面紧跟着它的结果。
- 没有结果的工具调用（运行中途被杀），推导时补一个"interrupted"结果，保证请求合法。

**为什么能命中缓存**：事件流只追加，所以每一次请求都是上一次请求的完整延续，包括跨轮次。只有压缩和修改系统提示词会让前缀变化一次。同一个聊天、配置不变时，拼出来的系统提示词逐字相同；开关一个模块、换一家服务或改配置，会让这个聊天的前缀变化一次。

**图片**：入库时下载，缩到模型实际看到的大小（聊天图片最长边 512px，`read_file` 的图片 1024px），转成 JPEG，单独存在 `gateway.images` 表里，事件里只记图片的键名。每次重放的都是同一份数据，所以以前的图片模型也能再看到。

实现见 [`src/conversation/`](../src/conversation/)：格式 `events.ts`、推导 `derive.ts`、恢复 `recovery.ts`、内存视图 `session.ts`。

## 请求

[`model.ts`](../src/agent/model.ts) 直接 `fetch` 调用 `POST {OPENAI_RESPONSES_BASE_URL}/responses`，不依赖 SDK，这样自定义参数可以原样透传。任何兼容 OpenAI Responses API 的服务都能用，默认是 OpenRouter。请求体为：

```
{ model, ...OPENAI_RESPONSES_EXTRA_BODY, instructions, input, tools, tool_choice }
```

网关按无状态的方式调用（不用 `previous_response_id`），`input` 就是从事件流推导出来的完整对话。思维链要原样回传，OpenRouter 会自动请求加密的思维链内容。用 OpenRouter 时，如果希望模型参考之前轮次的思维链，在 `OPENAI_RESPONSES_EXTRA_BODY` 里加上 `"reasoning":{"context":"all_turns"}`。

## 说话与挂断

模型只能通过工具行动，每次请求都设置 `tool_choice: "required"`：

- **说话**：调用 `send_message`，一次就是一条消息。想显示引用框时用 `reply_to`（填"第N条"里的 N）加 `quote: true`；不填 `reply_to` 时由运行时挂到这一轮合适的消息上。每条消息最多回复 5 次（文字、表情包、文件合计；上限由渠道适配器的 `maxRepliesPerMessage` 决定，不设置时默认 5），这个计数和 QQ 的 `msg_seq` 一起存在库里，跨轮次延续。
- **挂断**：说完后调用 `end_turn`，通常和最后一条消息放在同一步，不会多一次模型调用。旁观时不想说话，就只调用 `end_turn`。
- **按角色区分工具**：循环不认工具名，只看工具声明的 `role`：`say`（`send_message`，最后一步强制调用它）、`talk`（`send_sticker`、`send_voice`、`send_file`，和 `say` 一样算发消息，发送失败就不挂断）、`hangup`（`end_turn`，由循环处理，不真正执行）。新增一个发消息的工具，只要声明 `role: "talk"`，不用改循环。
- **同一步的执行顺序**：一步里的所有调用都按模型给出的顺序执行，`end_turn` 放在什么位置都一样，整步执行完才结束这一轮。
- **发送失败先不挂断**：挂断的那一步里如果有消息发送失败，这一轮就先不结束，让模型看到错误再决定怎么办（比如回复窗口过期、回复次数用满时换一条消息回复）。
- **平台连不上就停**：连接 QQ / Telegram 接口时如果连不上（连接超时、DNS 失败等），先等 1 秒自动重试一次；连接没建立说明请求没到平台，重试不会发出重复消息。还是不行，或者平台返回 5xx，这次运行就不再发送：后面的发送直接报错，模型看到“连不上，别重试，调用 end_turn”，这一轮在这一步后结束（`turn/end` 的原因是 `unreachable`），也不再接着处理新消息，留给下一次运行重试。实现见 [`src/channels/net.ts`](../src/channels/net.ts) 和 [`src/runtime/outbox.ts`](../src/runtime/outbox.ts)。
- **兜底**：如果服务商没有遵守 `required`、模型直接输出了文字，私聊或被 @ 时会把这段文字发出去。

| 可选的 `tool_choice` | 含义 |
|---|---|
| `"auto"` | 模型自己决定是否调用工具 |
| `"required"` | 必须至少调用一个工具（本项目的默认设置） |
| `"none"` | 不允许调用工具（压缩摘要时使用） |
| `{"type":"function","name":"…"}` | 必须调用指定的工具（本项目在最后一步强制 `send_message`） |

## 步数与时间

- **步数**：一轮最多 40 步，旁观轮次也一样（不插话时只调用 `end_turn`，1 步就结束）。
- **步数用完，最后一步必须发消息**：追加一条系统提示，告诉模型步数用完了；同时把 `tool_choice` 设为必须调用 `send_message`（角色为 `say` 的工具），让它说出目前的结果，没做完就说做到哪了。如果默认消息已经回复满 5 次，就直接结束。
- **时间**：函数最长运行 300 秒（`AGENT_MAX_DURATION_SECONDS`），所有规则写在 [`src/agent/budget.ts`](../src/agent/budget.ts)：
  - **剩余不到 100 秒，不开新的一步**：这一轮以 `paused` 结束，游标不动，交给一个新的 worker。中间不会强行收尾，也不会多发一句"还没做完"。
  - **每次调用都要在截止前 20 秒结束**：模型请求的超时是"剩余时间减 20 秒"（同时不超过 `OPENAI_RESPONSES_TIMEOUT_MS`，默认 280 秒）；`bash`、画图、语音、联网搜索等工具的超时也按这个缩短；剩不到 5 秒时工具直接不执行，告诉模型"换个函数再调"。这 20 秒用来写库和交接，函数就不会在调用中途被平台杀掉。
  - **模型请求超时或临时出错**（超时、断网、429、5xx）：这一轮以 `interrupted` 结束，游标不动，交给新的 worker 重试这一步。其他错误（比如 4xx）照旧算失败，回一句"出错了"。
  - **模型 key 没钱了**（402，或 OpenRouter 403 "Key limit exceeded"）：这一轮失败、游标前移，不重试。被 @ 和私聊回一句"没余额了"（报错里带重置时间就附上北京时间）；没 @ 的群消息不出声。日志只打一行 warn。
  - **接着跑**：新的 worker 发现上一轮是 `paused` 或 `interrupted`、消息还没处理完，就开一轮"接着上一段继续"，不经过旁观采样。模型能在事件流里看到之前做过什么、发过什么，系统提示让它从停下的地方接着做、不要重复发消息。函数中途被杀、由崩溃恢复补上的一轮也是 `interrupted`，同样会被接着跑。
  - **连续中断就放弃**：同一件事连续 2 轮都是 `interrupted`（每一轮都已经有一个完整的函数），说明它在一个函数里做不完，就放弃：游标推进，直接回复的消息会收到"这件事每次做到一半都超时了……"。中间有 `paused` 说明有进展，会重新计数。
  - **同步渠道**（HTTP）没法换函数，保留原来的做法：剩余不到 90 秒时下一步就是最后一步，必须发消息；剩余不到 120 秒就不开新的一轮，剩下的消息等下一个请求。
- **交给 worker 失败**：重试两次（间隔 1 秒、3 秒）后还连不上，这一轮留在事件流里，下一条消息的运行会接着做。
- **发不出去**（QQ 群消息 5 分钟后不能再回复，改发的主动消息又被拒收）：做得久的一轮，结果可能发不出去。错误里告诉模型别再挑旧消息重试、挂断这一轮；之后每一轮开头都会提醒它"之前有 N 条消息没能发出去：「……」"，直到它成功发出一条消息为止，所以下次群里有人说话时，它会把结果补上。实现见 [`src/conversation/undelivered.ts`](../src/conversation/undelivered.ts)。

## 上下文压缩

参照 dsh 的 compaction-basic：

- **触发**：模型返回的 `usage.input_tokens` 超过 `AGENT_CONTEXT_TOKENS`（默认 20 万）的 80%。这个数是服务商给出的准确值，不用自己估算。
- **保留**：最近约 16% 的内容保持原文，之前的部分做摘要。切点只会落在一轮的开始，或者不在任何一步之内的消息上，工具调用和它的结果不会被拆开；当前这一轮要回复的消息也不会被摘要掉。
- **摘要调用照顾缓存**：原样重放刚才那次请求的前缀（同样的系统提示词、工具和开头的输入），在末尾追加一条"请压缩上面的对话"，所以能命中服务商已经缓存的内容。
- **结果**：追加一条 `compaction/summary`，然后从存储里删掉被替代的事件和它们引用的图片。dsh 的日志存本地、永不删除；我们的免费数据库空间有限，所以要删。

实现见 [`src/agent/compaction.ts`](../src/agent/compaction.ts)。

## 崩溃恢复

运行者拿到锁后，先检查最后一轮有没有正常结束。如果函数中途被杀，留下了没结束的一轮：
- 给每个没有结果的工具调用补一条 `tool/result`。有 `tool/call` 标记的，结果写"可能已经生效"，比如消息可能已经发出去了；没有标记的，写"还没执行"。
- 补上 `step/end` 和 `turn/end`（原因 `interrupted`）。

和 dsh 一样，中断的轮次是"补完关闭"，而不是截断删除。这一轮的消息没有推进游标，下一轮会重新处理，模型从事件流里能看到上次做到哪里被打断了。

## 消息头

每条用户消息的第一行是消息头，推导时加上编号：

```
[第40条｜2026/11/03周二 20:43 Asia/Shanghai｜群聊｜发送人 老王 #3B6834｜@你]
大肥鱼你又在摸鱼？
```

- **第N条**：消息编号，就是事件的 seq，`reply_to` 填这个数。
- **时间**：让模型始终知道"现在"，时区由 `AGENT_TIMEZONE` 设置。
- **发送人**：平台用户 ID 的后 6 位作为编号，平台提供昵称时一并显示。QQ 只提供每个机器人独立的 openid，同一个人在私聊和群里的编号不同。
- **`@你`**：群里被 @ 的消息会带上这个标记。

## 存储结构

参照 dsh：会话头（这是谁的会话、在哪个渠道）放在日志之外，日志本身只追加。表在私有 schema `gateway` 里，见 [`supabase/schema.sql`](../supabase/schema.sql)：

| 表 | 内容 |
|---|---|
| `sessions` | 每个聊天一行：渠道、会话 ID、群聊还是私聊、域名（供启动 worker），格式版本，下一个 seq，游标（已处理到的最后一条用户消息），轮次计数，运行锁（持有者、到期时间），旁观采样窗口 |
| `events` | 事件流：主键 `(chat, seq)`，`type`，`time`，`data`（jsonb）。`turn`、`step` 是从 `data` 生成的列，方便在表格编辑器里筛选 |
| `replies` | 每条消息的回复状态（QQ 的 msg_seq、已回复次数），主键 `(chat, event_id)` |
| `images` | 图片（data URL），键名形如 `ev:img:{聊天}:{消息}:{n}` |
| `inbound` | 已经收到过的平台事件 ID，用来识别平台重推，保留 1 小时 |

`events`、`replies` 对 `sessions` 有外键并级联删除，删掉一个会话就删掉它的全部数据。代码通过 `public` 里的函数访问这些表（[`src/adapters/supabase/store.ts`](../src/adapters/supabase/store.ts)），每个操作一次请求：

| 函数 | 作用 |
|---|---|
| `chat_ingest` | 入口：去重、建会话、追加事件、按需抢锁，一个事务 |
| `chat_open` | 读会话行和某个 seq 之后的事件 |
| `chat_append` | 追加一批事件，返回第一个 seq |
| `chat_trim` | 删掉某个 seq 之前的事件和它们引用的图片（压缩后） |
| `chat_lock` / `chat_claim_ambient` | 运行锁的获取、续期、释放；旁观采样 |
| `chat_begin_turn` / `chat_set_cursor` | 轮次计数、游标 |
| `reply_get` / `reply_put`、`image_put` / `image_get` | 回复状态、图片 |
| `gateway_expire` | 每天清理：删除 7 天没有新消息的会话，以及过期的用量和操作记录 |

发送 `/reset` 会删除当前会话之前的全部事件、图片和回复状态，seq 继续往后编号。

管理端另有几张表，都不挂在 `sessions` 上，会话过期以后它们还在，详见[管理端](admin.md)：

| 表 | 内容 |
|---|---|
| `meta` | 表结构版本号 |
| `settings` | 管理端里填的配置，按环境变量名存；配置目录里标为密钥的，管理端只显示打码后的样子 |
| `chat_profiles` | 每个聊天的设置：备注名、回复方式、插话频率、工具开关、额外设定、额度 |
| `usage_daily` | 每个聊天每个 UTC 日的用量（轮次、token、花费、画图 / 语音 / 搜索次数） |
| `admin_log`、`admin_login_failures` | 管理操作记录；登录失败次数 |

每个聊天的设置会影响一轮对话：

- 系统提示后面会加上这个聊天的额外设定。
- 关掉的工具不提供给模型。
- 当天的花费额度用完时不开新的一轮。
- 一轮结束后，用量从这一轮的事件里累加，见 [`src/chats/usage.ts`](../src/chats/usage.ts)。

“只记录”模式下收到的消息带 `quiet` 标记，模型以后能看到它们，但它们不算待处理的消息。

管理员代发的话记为 `admin/message`，模型会把它当成自己说过的话。

机器人每发出一条内容（不管是工具发的，还是运行时自己发的提示），都会记一条 `bot/sent`。它只写日志，不进模型输入，管理端的聊天记录就是从 `user/message`、`bot/sent`、`admin/message` 渲染出来的。
